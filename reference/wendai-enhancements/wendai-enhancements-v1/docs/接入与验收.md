# 接入与验收：参考路径，以实际项目为准

没有收到现有仓库，不能假定你们组件名、路由、状态库或真实后端权限已经正确。以下明确给出复制位置和调用顺序；不要整包覆盖现有cash-engine、权限与账本。

## 1. 文件放置与最小启动

把本包的 `core/`、`data/`、`react/` 按原相对层级复制至：

```text
src/features/wendaiEnhancements/
  core/...
  data/...
  react/EnhancementPanel.tsx
  react/Example.tsx
  react/enhancements.css
```

Vite中的 `src/App.tsx` 可临时使用：

```tsx
import Example from './features/wendaiEnhancements/react/Example';
export default function App(){ return <Example/>; }
```

计算核心没有第三方依赖。React组件使用现有React；`.mjs`配套`.d.mts`用于类型解析。Vite的TypeScript建议 `module:ESNext`、`moduleResolution:Bundler`、`jsx:react-jsx`，保留项目已有的CSS声明，例如 `vite/client`。不要为这3个模块新增后端。

如果团队的现有 `CashEvent` 字段名不一样，只修改 `core/adapter.mjs` 的入参映射和对应 `.d.mts`，保留以下语义。先通过本包测试，再写一份从你们真实项目DTO到本包DTO的契约测试。

## 2. 输入契约

### CashEvent

| 字段 | 类型/含义 | 不可偷换的语义 |
|---|---|---|
| id、cashKey | string，事件ID与现金动作稳定ID | 一个收款订单和一次对应结算不能各算一次现金 |
| merchantId | string | 不跨商户聚合 |
| kind | settlement/purchase/rent/refund/tax/transfer/ownerDraw | 不认识的类型拒绝 |
| amountCents | 非负安全整数 | 单位分，不用浮点元乘100入账 |
| direction | in/out | 用方向决定正负；不混负amount |
| at | UTC epoch毫秒 | 现金预计/实际可用时点，界面按北京时间 |
| status | planned/pending/posted/voided | pending不代表已经计入B₀ |
| currency、scope | CNY、business | 家庭明细不能放进经营预测 |
| confirmed、sourceRefs、version | boolean、string[]、整数≥1 | 确认的是来源/预计事项，不能把模型输出点一下就当银行到账凭证 |
| includedInOpening | posted必须为true | 已入B₀的已到账款不能再次加钱 |
| transferScope | inside/outside | inside同一余额口径内互转净额0；未知范围拒绝 |
| provenance | confirmed/forecast | forecast直接拒绝投入确定性账本 |
| channel | string | 指定延期款与历史统计必须同渠道 |

状态映射：planned/pending→scheduled；posted→included_in_opening；voided→cancelled。不覆盖你们真实状态机。恰好发生在asOf时的款项必须先与B₀对账，不能同时作为待发生事件。

### EnhancementBundle

`merchantId,revision,historyRevision,asOf,end,openingCents,reserveCents,reserveChanges?,balanceConfirmed,obligationsConfirmed,events,history,settlements,delayTargetIds`。

- `history`为日常到账/采购的完整闭合日序列，连续、同一商户、有来源。84天是演示，不是银行最低样本标准。
- `settlements`为预计/实际到账配对记录：id,merchantId,channel,scheduledAt,knownAt,actualAt?,status,sourceRef。
- `delayTargetIds`需有至少一笔指定待结算款，且同商户同渠道。这个接入示例专门面向有结算时间差场景；没有这类款项时，你们可直接调用forecast/reserve模块，不要伪造一个延期目标。
- `reserveChanges`继续兼容时变留底。采用建议时，将所有未来留底不低于建议值。

### 返回对象

`computeEnhancements(bundle,options)`返回：baseline（只按计划）、stress（所有延期情景）、withReserve（确认后留底的联合结果）、forecast、settlement、reserveAdvice、blocks、basisKey、两类revision。

`options`：delayDays、delayQuantile、reserveQuantile、reserveConfirmed。默认2、.9、.9、false。这些都要在参数说明中可见，不称风险概率。

## 3. 调用顺序

1. 现有账本解析/去重/来源确认 → 更新CashEvent版本与账本revision。
2. 已完成历史记录与完整日历 → `aggregateDaily` → `DailyCash[]`。真实数据回溯修订时还需历史版本仓库，此处未实现。
3. 构造Bundle → `computeEnhancements(bundle,{delayDays:2})`。
4. 内部先 `settlementStats → buildDelayScenarios → toEngineInput → evaluate`，输出原条件结果。历史预测不可用不能抹掉正确的已确认事件结果。
5. 再 `evaluateForecasts → bufferBlocks → recommendReserve`，输出独立预测与待确认建议。
6. 展示来源/原留底/建议/影响 → 商户明确确认 → 应用新的reserve并重新计算。没有确认，原结果不变。
7. 任何金额、日期、状态、版本、来源、历史或参数更正 → 清除旧确认与缓存 → 全量重算。小数据不值得维护复杂增量缓存。

```js
import {computeEnhancements,isResultCurrent} from './core/adapter.mjs';
const options={delayDays:2,reserveConfirmed:false};
const result=computeEnhancements(bundle,options);
if(!isResultCurrent(result,bundle,options)) throw Error('RESULT_STALE');
// 显示 result.forecast，但不能写成 confirmed CashEvent。
// 只有本人确认后才使用 result.withReserve 的确认版本：
const confirmed=computeEnhancements(bundle,{...options,reserveConfirmed:true});
```

**上面最后一行必须在点击确认的事件处理器中执行，不能在useEffect中自动执行。** React组件已示范；它在依据变化后自动使本页模拟确认失效。

## 4. 原项目采用留底：父组件事务示例

下面路径与状态存储名是参考；代码假定你的 `bundle` 已按本契约规范化。单机使用函数式setState，若将来真实多用户服务必须服务器鉴权和版本冲突检查。

```tsx
<EnhancementPanel
  bundle={bundle}
  onOpenSource={sourceRef => openExistingSourceDrawer(sourceRef)}
  onConfirmReserve={change => setBundle(current => {
    const currentResult=computeEnhancements(current,{delayDays:change.delayDays});
    if(current.revision!==change.expectedRevision ||
       current.historyRevision!==change.expectedHistoryRevision ||
       currentResult.basisKey!==change.basisKey ||
       currentResult.reserveAdvice?.suggestedReserveCents!==change.reserveCents) {
      return current; // 同时在页面显示“依据已更正，请重新查看并确认”
    }
    return {...current,revision:current.revision+1,reserveCents:change.reserveCents,
      reserveChanges:(current.reserveChanges??[]).map(r=>({...r,cents:Math.max(r.cents,change.reserveCents)}))};
  })}
/>
```

`basisKey`是内部完整JSON签名，不是加密哈希或防篡改证据；里面可能含原始字段，**不放进家庭/银行分享包**。数据库中仍需记录确认人、确认时间、所用版本；本包只做单机模拟。

## 5. 商户三屏如何放

- 屏1不增加预测输入：仍确认已到账可用余额。预测款绝不能出现在“当前可用”。
- 屏2仍核对采购、房租、退款、税款等义务；增加“留底建议”折叠卡，默认不应用。税款按商户提供计划保留，不自动估税。
- 屏3保留可提用结论为首层；下方依次放“这笔结算晚到几天”“接下来7个日历日的日常收付预测”“留底依据”。缺资料用文字，不能把null显示成0；不可行的0要写“即使不拿也不足”。
- 图表：确定性余额继续阶梯线；日额预测用另一张图或日期表，不能把预测收入叠加到硬约束余额，也不能称每日净流入为利润。
- 点击预测日期/留底依据调用 `onOpenSource`。来源面板显示原始记录版本；本包React示例仅弹出来源ID，占位不是你们现有抽屉的完成接入。
- 历史页面保存run的两类revision、参数、来源。重算后旧run标过期，不能继续按钮确认。

## 6. 经营咨询与家庭分享

新增forecast、reserve、basisKey或完整历史，不得通过对象展开自动流入现有分享DTO。保留原白名单；经营咨询最多由商户主动选定结算事实/待核对的问题。家用明细、推导出的总余额和可拿额度不默认给银行。前端白名单不等于服务器权限隔离；本包没有真实后端、用户鉴权或跨角色安全保证。

## 7. 合并步骤与验收

1. 备份分支，只复制新目录，不替换原内核。跑本包测试。
2. 挂Example临时路由，以3模拟商户确认页面能渲染；运行项目原有typecheck/build。
3. 将现有对象映射到Bundle；先用原案例确认按时1200、延期不可行0、200/800缺口。
4. 接来源抽屉、两类revision、确认按钮；手动更正来源日期，确认旧结果失效。
5. 把当前余额改600、留底600，在只有以后收款且无其他支出的独立用例中必须可行0；不能从未来收入借今天的可提用额。
6. 把预测到账扩大10倍，已确认事件不变，硬上限仍不变；延迟收款不得提高同组联合上限。
7. 应用800元建议后按时上限1000；联合延期仍不可行；不能显示“模型已经消除缺口”。
8. 切水果店看失败警示与真实留出误差；不能删除不好看的样本。
9. 检查分享网络请求与DTO不多带新字段；真实后端有权限实现时做对应服务端测试。
10. 录90秒演示，并保留模拟/已实现/待接入标签。
